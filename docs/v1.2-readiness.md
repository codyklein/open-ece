# OpenECE 1.2.0 — bounded release-readiness review

Review starts from accepted checkpoint 4,
`c799175b6744b0dbe674d68d68ca4d8c36c5c909`, against published 1.1.0 at
`08722869a9fc771f56397c46cd54c983402f36e6`. This is candidate documentation, not
publication or physical-candidate acceptance. The final checkpoint report supplies
the exact candidate commit, CI run, unsigned artifact and independently checked hash.

## Scope and source review

The 1.2 feature diff adds presentation and tests under `gui/schematic/`, the shared
`gui/circuit_presentation.*` wrapper and small DC/AC/Transient view adapters. It
does not change numerical engines, engineering APIs, the project codec/schema,
release-pinned fixtures or published assets. Candidate preparation changes central
version/package metadata, documentation and validation gates; it adds no dependency.

| Review area | Contract / evidence |
| --- | --- |
| Projection | `model.hpp` / `projection.cpp`: owned raw data, distinct NodeKey/ComponentKey scoped by analysis, exact declared/dangling/unselected references; no solver, allocation of IDs or parsing. |
| Layout | `layout.*`, `layout_geometry.cpp`, `layout_verify.cpp`: bounded integer geometry, deterministic structured recognition and net-rail fallback; complete independent verification before display. Crossings do not union nets. |
| Rendering | `qt/render_geometry.cpp`: exact routes with under-wire gaps, polarity-aware vector glyphs and measured/elided labels; full originals remain available. Highlight width retains gaps. |
| Ownership | `qt/canvas.cpp`: State owns graph/diagram, Qt parents own scene/widgets, scene owns items; callbacks refer only to the owning canvas. Replacement blocks tree signals before clearing; destruction clears callbacks/items before State dies. |
| Host lifecycle | `circuit_presentation.cpp`: owner-scoped borrowed callback, lazy canvas, QObject-context queued refresh, coalescing and graph equality; queued work is cancelled with the widget. No execution timer is added. Failure clears the old scene. |
| Read-only | The wrapper synchronizes exact pending text, then projects authoritative state. Navigation/inspection have no editing path. No calls to numerical solving, simulation controls, allocator updates or project I/O are introduced. |
| Integration | Existing tabs/IDs and retained tables remain; DC results, AC sweeps and Transient frozen traces/workers remain separate. Initial splitter sizing occurs once after layout; later navigation preserves the user's split. |
| Persistence | Schema 1 import/schema 2 save, confirmation on in-place upgrades, inert restore and exact raw drafts remain. View choice/geometry/selection are transient and absent from serialized state. |

The production-workspace tests cover exact pending delegates/line text, all three
analyses, typed selection/deletion, failure clearing, results/lifecycle retention,
New/Open/save round trips, clean navigation, active execution teardown and queued
refresh destruction at four scale factors. Existing assertions are retained.
ASan/UBSan covers destruction/replacement. This is not a formal proof or native
accessibility certification.

The accepted source review found no numerical, persistence or connectivity blocker.
The stricter candidate tests subsequently reproduced a tiny-text painting defect
on Windows; its evidence and narrow rendering correction are recorded below.
Exact-candidate validation remains a gate.

## Windows painter warnings — evidence, reproduction and risk

Accepted checkpoint-4 run [38849050218](https://github.com/codyklein/open-ece/actions/runs/38849050218)
matches checkpoint 3's warning counts: at Qt scale 1 / 1.25 / 1.5 / 2, respectively
232 / 952 / 960 / 960 warnings in **each** MSVC configuration. They occur in
`SchematicGuiTest::replacementFailureAndDensity()`, not the production workspace
integration cases or Release renderer benchmark. The four messages are:

```text
QPainter::begin: Paint device returned engine == 0, type: 3
QPainter::setCompositionMode: Painter not active
QPainter::fillRect: Painter not active
QPainter::end: Painter not active, aborted
```

Reproduce with the existing native Windows Qt 6.8.3 SDK/runtime:

```powershell
$env:QT_QPA_PLATFORM = 'windows'
$env:QT_SCALE_FACTOR = '1.5'
.\build\windows\tests\Debug\openece_schematic_gui_tests.exe replacementFailureAndDensity
.\build\windows\tests\Debug\openece_schematic_gui_tests.exe settledViewportRendering
```

The first test replaces all eight fixtures twice and paints directly into an
800×600 image **without event-loop/layout settling between replacements**. It also
constructs/destroys three hidden temporary canvases. Candidate diagnostics bracket
each install, image render and hidden temporary; viewport size/transform are logged.
The destination QImage and outer QPainter now have explicit validity/active/end
assertions. These assertions distinguish an outer paint failure from diagnostics
inside Qt; they do not prove every internal paint operation succeeded.

The new `settledViewportRendering()` exercises the same fixtures (including 128
components / 7,936 crossings) after native exposure/event processing, Fit, zoom/
scroll and net selection. Four additional CTest cases run it in fresh processes
at 100/125/150/200%, independent of earlier glyph/scene state. The original stress
test keeps its prior ordering; the new settled test does not prime it. Any
QPainter warning fails either test. Production-workspace
tests likewise fail on QPainter warnings. Fresh packaged persistence additionally
rejects such diagnostics. The original stress operations and assertions remain;
there is no ignore handler, severity downgrade, message filter or test disable.
Qt's [filtered failOnWarning API](https://doc.qt.io/qt-6.8/qtest.html#failOnWarning)
is scoped to each test function.

The initial checkpoint-5 validation run
[38934563672](https://github.com/codyklein/open-ece/actions/runs/38934563672)
**failed** the new strict settled gate on Windows Debug when fitting the maximum
density fixture. Therefore the earlier stress-only risk classification was not
sufficient: the same condition was reproducible after normal layout settling.
The outer image and painter remained valid. All six Fedora jobs passed; Windows
Release and the fresh package job did not run. No candidate from that failed run
is approved.

Investigation identified the matching upstream Qt issue. In Qt 6.8.3,
`QImageTextureGlyphCache::fillTexture()` obtains a glyph mask without checking for
a null image, then constructs an image painter, sets its composition mode, fills
and ends it. These are the four warning operations above. Qt's
[upstream correction 9ab79b4b](https://github.com/qt/qtbase/commit/9ab79b4b578e44404a0c66d9b3db8d9f45697426)
explicitly describes empty glyph images at very small Graphics View transforms
and adds the null check. The dense fixture's logged Fit transform was about
0.0268, taking ordinary label glyphs below one device pixel. Fedora's newer Qt
6.11.2 already includes that guard. This evidence explains why successful ordinary
workspace/benchmark tests and prior physical acceptance did not exclude the issue.

The narrow renderer correction retains the Qt pin, label geometry and all text.
`LabelItem` uses Qt-shaped vector text outlines when the transformed font height
is below eight device pixels; at readable sizes it uses the existing native simple
text item. It does not hide labels, change measured extents, modify circuit geometry
or filter diagnostics. Both paths retain full raw inspector/tooltip text and the
same single-line display/elision policy. Device transform includes DPI and render
target scaling. This avoids the affected tiny RGB glyph-cache operation without
introducing a dependency upgrade or changing normal-size label rendering.

Regression coverage renders the actual scene labels at transforms 0.0001, 0.025,
0.1, 0.25, 1 and 2, checks unchanged text/bounds and visible ink at readable sizes,
and fails on painter warnings. The original rapid replacement stress now also
fails on any painter warning, as do the settled, workspace and packaged gates.
No old test is disabled and no warning handler suppresses messages. Final CI must
pass these gates at all four scale factors before candidate handoff. Physical
candidate review must include zooming out/back and checking labels/inspection.
Virtual-monitor geometry messages below are a separate issue.

## Virtual-monitor geometry warnings

Native Windows CI reports `QWindowsWindow::setGeometry` when tests request sizes
that its HyperVMonitor or enlarged-font standalone-editor minimum cannot supply.
For example, the checkpoint-4 700×550 standalone DC request resulted in 700×907.
This is distinct from painter state and electrical geometry. These warnings are
retained. Production hosts use an outer scroll area; Transient has the accepted
noncollapsible scrolling splitter. Tests check reachable content/focus and the
user accepted the real integrated layouts. This does not establish every physical
DPI/window combination: repeat smaller-window, scaling and enlarged-font checks
on the exact candidate. An unreachable primary control is a release blocker.

## Resource and performance review

Unchanged limits: 32 nodes, 128 components, 256 terminals, 1,024 wire segments,
1,024 junctions, 16,384 crossing markers, 416 labels, 20,000 primitives, 2 million
counted operations, 32 MiB conservative layout working-storage estimate and
absolute coordinates ≤1 million units. Source-text/point budgets also remain.
These are not whole-process or Qt raster-allocation limits.

Release renderer observations from accepted CI, milliseconds (five-iteration
medians; each setup uses a warm-up):

| Platform/run | Divider scene + verify | Dense scene + verify | Dense first paint | Dense zoom/scroll/paint | Dense net inspection | Process peak bytes |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Windows Qt 6.8.3, checkpoint 3 / 38825675399 | 1.110 | 27.116 | 10.785 | 4.887 | 25.581 | 110145536 |
| Windows Qt 6.8.3, checkpoint 4 / 38849050218 | 1.149 | 27.675 | 11.527 | 5.217 | 26.436 | 110637056 |
| Fedora Qt 6.11.2 offscreen, checkpoint 4 / 38849050218 | 0.708 | 15.235 | 8.554 | 3.934 | 18.464 | 84295680 |

The dense scene contains 611 items, not one item per crossing. Checkpoint-4 measured
dense layout+verification on Windows used 1,425,142 counted operations and a
10,335,244-byte conservative working bound. Large retained source metadata used
23,675,216 bytes by that estimator. Qt peak measurements include loader, fixtures,
scene and image buffers and are not per-diagram allocation. Platform/runner noise
and different Qt versions preclude exact cross-platform comparisons.

No material regression requiring a new architecture was evident between the
accepted checkpoints. Final CI repeats layout/render benchmarks; compare its logs
with these records before candidate handoff. These observations are not exact
frame-rate, latency or memory guarantees. Ordinary progress, focus, selection and
navigation do not rebuild a scene; represented-data edits are coalesced and only
changed graphs are reinstalled.

## Release gates and deferrals

Require all six Fedora configurations, MSVC Debug/Release, fresh extracted runtime,
strict settled/workspace painting, unchanged compatibility fixtures, examples,
format/diff and complete package-manifest checks at the final commit. The checkpoint
report must state any failure/pending item and identify the exact unsigned ZIP.
Version comes from CMake 1.2.0; About and PE resources consume it. Explicit workflow
names/stage guard are checked against CMake. Action pins, OIDC, publisher, protected
environment, vendor verification, timestamps and two-target signing policy remain.
Push/PR CI is unsigned; protected signing has not been authorized by checkpoint 5.

Final recommendation is **conditional on those gates**: ready for bounded physical
candidate testing if they pass, otherwise blocked with the concrete failures.
Fedora/Windows candidate acceptance and future signed-ZIP acceptance are pending.
Use [the exact-candidate checklist](v1.2-candidate.md). No merge, tag or publication
is implied. Graphical editing/wiring/positions, overlays/export, undo/redo, new
solvers, schema changes, dependency churn and unrelated polish remain deferred.
